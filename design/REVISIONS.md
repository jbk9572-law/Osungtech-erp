# 수정사항 기록 (REVISIONS)

사용자가 화면에서 발견한 어긋남·개선 의견을 **코딩 전에 먼저 기록**하는 목록이다. 상태: 대기(기록만) → 진행 → 완료. 항목마다 원인(코드로 추정한 것 포함)과 같은 구조가 몇 곳인지(전수조사)를 적는다.

## R-001 · 수량 칸 힌트 글자 제거 — 상태: 대기(사용자 결정 완료, 코딩 전)

- **제안(사용자, 2026-11-23)**: 수량 칸 안의 "수량 (엑셀식 계산 가능)" 안내 글자는 빼는 게 낫다. 칸이 좁아 글자가 잘리고 오히려 복잡하다. **기능을 빼자는 것이 아니다.**
- **현재 코드**: `src/components/quantity-with-box-input.tsx` 50행 — 수식 입력이 켜져 있으면 placeholder가 `수량 (엑셀식 계산 가능)`. 포장 기준이 있으면 `수량 (예: 12×1=12)`.
- **같은 구조(전수)**: `QuantityWithBoxInput`을 쓰는 화면 5곳(매출 전표, 매입 전표, 할일 품목, 재고 조정, 재고 실사) — 부품 한 곳을 고치면 모두 같이 바뀐다.
- **계획**
  1. placeholder는 `수량` 한 단어로 통일한다. **결정(사용자, 2026-11-23): 포장 기준 예시 문구 `(예: 12×1=12)`도 같은 이유로 뺀다.**
  2. 수식 입력 기능은 그대로 둔다. 안내는 칸에 포커스가 갔을 때만 보이는 툴팁/`title`(예: `12*3처럼 계산식을 입력할 수 있습니다`)로 옮긴다.
  3. 표 머리 `수량`의 `title`에도 같은 안내를 둔다.
- **주의**: 수식 칸임을 알려 주는 표시(예: 머리글 파란 글씨)가 이미 있다 — 그 표시는 유지.

## R-002 · 표 안 입력칸 모양 불일치 — 규격·단가만 둥근 테두리 — 상태: 대기(사용자 결정 완료, 코딩 전)

- **발견(사용자, 2026-11-23)**: 매출전표 입력 표에서 규격·단가 칸만 둥근 테두리 입력칸이고, 품목·관리번호·수량·금액은 테두리가 없다. "이게 맞나?"
- **판단: 맞지 않다(일관성 위반).** 같은 표 안의 입력칸은 한 가지 모양이어야 한다(디자인 규칙: 규격표 §7 블록 규칙, 엑셀식 표는 셀 입력 하나).
- **원인(코드로 추정)**: `src/components/new-sale-form.tsx` 1354행(규격)·1405행(단가)이 `className="erp-input w-full"`로 테두리 있는 일반 입력 클래스를 직접 지정하고, 품목·관리번호·수량 등은 클래스를 주지 않아 표 칸 기본 모양(테두리 없음)으로 나온다. 확인 못 함: 모든 칸의 최종 CSS를 화면에서 열어 보지는 않았다.
- **같은 구조(전수)**: `className="erp-input w-full"`가 컴포넌트 **30개 파일 92곳**. 이 중 표(`<td>`) 안에 있는 것이 전표·입력 표 대상이고, 정확한 개수는 작업 시작 때 다시 센다.
- **계획**
  1. 표 안 입력칸용 공용 클래스 하나(예: `erp-cell-input`)를 정한다 — 엑셀식: 평소엔 테두리 없음, 포커스 때 파란 테두리, 읽기 전용은 옅은 배경. 값은 규칙표 토큰만 사용.
  2. 표 안 `erp-input w-full` 호출부를 그 클래스로 바꾼다(자동 변환 + lint로 재발 방지: 표 안에서 `erp-input` 직접 사용 금지).
  3. 위 예외(넓은 전표 그리드 `wide-voucher-grid`)는 폭만 면제이고 이 모양 규칙은 지킨다.
- **결정(사용자, 2026-11-23): 추천대로.** 표 안 입력칸은 테두리 없음 + 포커스 때만 파란 테두리, 입력 가능한 칸은 옅은 바닥색으로 보완한다.

## R-003 · 매출 목록 도구 줄 정리 — 버튼 5개 → 표준 동작 + "일괄 작업 ▾" — 상태: 대기(사용자 결정 완료, 코딩 전)

- **발견(사용자, 2026-11-23)**: 도구 줄을 맨 위로 올렸더니 버튼이 `F2 신규 / 빠른등록(매출·수금·반품) / 엑셀 다운로드 / 홈택스 일괄발급 엑셀 / 세금계산서 일괄 작성` 5개가 한 줄에 늘어서 오히려 UI가 나빠졌다.
- **판단**: 표준 동작(조회·신규·수정·삭제·엑셀)을 맨 위 도구 줄에 두는 것은 맞다(시안과 같고 모든 목록에서 같은 위치). **이 화면 전용 동작까지 맨 위에 늘어놓는 것은 맞지 않다**(줄이 길어지고, 중요한 버튼이 묻히고, 표에서 멀다).
- **나빠 보이는 이유(사진 기준)**: ① 버튼 5개·긴 이름 ② 첫 버튼만 파랑+F2 표시, 나머지는 테두리 ③ 아이콘 색이 제각각(주황·파랑·회색) ④ 중요도 구분 없음.
- **결정(사용자): 추천대로.** 도구 줄 = `조회·신규·수정·삭제 | 엑셀 | 일괄 작업 ▾`. 빠른등록·홈택스 일괄발급 엑셀·세금계산서 일괄 작성은 "일괄 작업 ▾" 메뉴로 묶는다. 아이콘은 단색, 버튼은 한 가지 모양(28px).
- **같은 구조(전수)**: 매출·매입 목록(`PageToolbar`)이 같은 방식 — 작업 시작 때 전용 동작이 있는 화면을 다시 센다.
- **연관**: "F2 신규" 라벨은 "표 안 F2 = 셀 편집" 결정과 충돌한다 → 신규의 새 단축키를 정해 라벨을 바꾼다(작업 시 사용자에게 확인).
- **확인 필요**: 세 전용 동작 중 매일 쓰는 것이 있으면 단독 버튼으로 남긴다(사용자가 알려 주기로 함).

## R-004 · 좌측 메뉴와 메인 대시보드의 비율·글자 크기 불일치 — 상태: 대기(기록만, 코딩 전)

- **발견(사용자, 2026-11-23, 배포 후 화면 캡처)**: 좌측 메뉴와 오른쪽 메인 대시보드 화면의 비율이 맞지 않고 텍스트 크기도 어울리지 않는다.
- **사진에서 보이는 것(코드 확인 전 관찰)**
  1. **글자 크기가 한 화면에 너무 여러 단계**: 메뉴 항목(작음) · 카드 제목(작음) · 카드 숫자 `0원`·`1,808,888,977원`(크고 굵은 고정폭 글꼴) · 달력 `21건`(아주 작음) · 탭 라벨. 규칙표의 글자 6단계(10.5/11/13/표12/15/19)를 벗어난 값이 섞여 있을 가능성이 크다.
  2. **메뉴 들여쓰기가 거꾸로**: 그룹 이름(▸ 그룹웨어, ▾ 매출관리)은 안쪽에서 시작하고 하위 항목(출고관리·출고처관리…)은 그보다 바깥쪽(왼쪽)에서 시작한다. 계층이 시각적으로 반대다.
  3. **대시보드 구조가 승인된 E형 시안과 다름**: 승인 시안은 `숫자 카드 4개 → 오늘 할 일·최근 전표 → 추이`. 현재는 안내 배너 + 빠른 버튼 줄 + 숫자 카드 5개(색 윗줄) + 2열 탭 목록 + 달력 + 오른쪽 리포트 패널.
  4. 오른쪽 리포트 패널과 마지막 카드가 화면 오른쪽에서 잘려 보인다(캡처 폭 때문일 수 있음 — 확인 못 함).
- **확인한 코드 사실**: 대시보드 전용 CSS(`.erp-dash*`)는 10개 규칙이고 글자 크기를 px로 직접 쓴 줄은 0개다. 즉 **대시보드 글자 크기는 `.erp-dash*` CSS가 아니라 다른 곳(컴포넌트의 직접 스타일 등)에서 정해진다.** 정확한 출처는 확인 못 함 — 작업 시작 때 화면에서 요소별 글자 크기를 재서 찾는다.
- **같은 구조(전수)**: 대시보드 화면 1개(`app/(dashboard)/dashboard`)와 메뉴 트리 1개 — 단, 같은 숫자 카드·탭 목록 패턴을 쓰는 다른 화면(미수금·재고 요약 등)이 있는지 작업 시작 때 센다.
- **계획**
  1. 메인 화면의 요소별 실제 글자 크기를 CI에서 재서 규칙표(6단계)와 어긋난 목록을 만든다(규칙표 점검에 대시보드 추가).
  2. 대시보드 글자를 규칙표 단계로 정리한다: 카드 제목 11px / 본문 13px / 숫자 19px(큰 숫자) / 달력·칩 10.5px.
  3. 좌측 메뉴 계층 들여쓰기를 바로잡는다(그룹 이름이 바깥, 하위 항목이 안쪽).
  4. 대시보드 구조를 E형 시안으로 옮길지 사용자와 결정한다(옮기면 기존 기능 중 빼는 것·유지하는 것을 먼저 정한다).
- **확인 필요**: 이 캡처가 배포 후(모던 규칙표 적용) 화면인지, 캐시된 이전 화면인지 — Ctrl+F5 후 같은 모양인지 알려 주면 좋다.

## R-005 · 게시판(그룹웨어) — "새 ○○" 버튼 4개와 오른쪽 인라인 수정이 규칙과 다름 — 상태: 대기(기록만, 코딩 전)

- **발견(사용자, 2026-11-23, 캡처)**: 게시판 목록 위에 `+ 새 공지 / + 새 인사문서 / + 새 공문 / + 새 기안` 버튼이 4개 있고, 오른쪽에서는 글이 **모달이 아니라 오른쪽 칸 안에서 바로 수정 폼**(제목·상단 고정·편집기)으로 바뀐다. "기존 규칙이랑 달라서 애매하다."
- **판단: 규칙과 다르다(일관성 위반).** 근거(승인된 규칙):
  1. 신규는 **도구 줄의 [신규] 하나**이고, 누르면 **C형 모달**(시안 H1 "새 글 쓰기")이 뜬다 — 목록 안에 "+ 새 ○○" 버튼을 여러 개 두지 않는다.
  2. B형(소통형)의 수정은 **C형 모달**이다. 오른쪽 칸은 읽기 전용 상세이며, 칸 안에서 편집 폼으로 바뀌지 않는다.
  3. 저장·삭제 키: 저장은 F7(라벨은 "저장" — 지금은 "F7 수정"), 삭제는 표준 삭제 동작(지금은 "F6 삭제"로 다름). 닫기는 Esc.
- **캡처에서 보이는 다른 어긋남**: ① 목록에 글이 8건 있는데도 맨 아래에 "위 + 버튼으로 새 글을 작성해보세요" 빈 화면 안내가 같이 나온다(빈 상태 문구가 항상 표시됨) ② 위쪽 파란 안내 박스가 길고 작은 글자로 3줄 설명 ③ 오른쪽 제목 `공지사항 > 수정`과 위의 `게시판` 제목이 이중 ④ 목록 항목마다 "공지" 작은 라벨 + 안읽음 빨간 점이 중복 표시.
- **결정 대기(추천안)**: 
  - **신규**: 도구 줄에 **[신규 ▾] 하나**. 왼쪽 필터 열에서 유형(공지·인사문서·공문·기안)을 고른 상태면 그 유형으로 바로 모달이 열리고, "전체"를 보고 있을 때만 유형 선택 메뉴가 뜬다. 단점: 전체 보기에서는 클릭이 한 번 더 필요하다.
  - **수정**: 오른쪽 칸은 읽기 전용으로 두고 [수정] → C형 모달. 단점: 지금처럼 바로 고치는 흐름이 한 단계 늘어난다.
  - 단축키: 저장 F7("저장"), 닫기 Esc, 삭제는 다른 목록과 같은 키(정확한 키는 R-003의 단축키 결정에 맞춘다).
- **같은 구조(전수 전 확인)**: 코드에서 `+ 새 ○○` 문구는 할일(`todos/modern.tsx` + 새 할일), 결재선(`approvals/lines/` + 새 결재선), 모조지 계산(+ 새 품목·+ 새 배치), 재고 실사(+ 새 실사 시작) 등에도 있다. 이 중 B형(할일·메일·게시판·공지·메신저)이 같은 규칙의 직접 대상 — 작업 시작 때 5개 화면을 다시 센다. 확인 못 함: 게시판 오른쪽 인라인 수정이 공지·결재 화면에도 같은 부품인지.
- **연관**: R-007("새 ○○" 위치 통일), R-003. 같은 규칙으로 함께 처리한다.
- **확인 필요**: 오른쪽 칸에서 바로 수정하는 흐름을 일부러 좋아하셨는지(편해서 유지하려는지), 아니면 규칙대로 모달로 통일해도 되는지.

## R-006 · 메신저 전체 리디자인 — 상태: 대기(기록만, 코딩 전)

- **발견(사용자, 2026-11-23, 캡처)**: "메신저도 리디자인해야 한다. 디자인이 형편없고 UI도 엉망이다."
- **판단: 동의한다.** 사진에서 보이는 문제(코드 확인 전 관찰):
  1. **왼쪽 열이 서로 다른 두 가지를 섞음**: 위는 대화 필터(전체·안읽음·1:1·그룹·알림 꺼짐), 아래는 사원 목록(검색 + 사원). 한 열에서 "무엇을 고르는지"가 불분명하다.
  2. **행 높이·글자가 제각각**: 필터 행은 약 30px, 사원 행은 약 47px로 간격이 넓고 아바타는 22px로 작다. 맨 위 "대화" 라벨은 10px 정도로 아주 작다. 규칙표(항목 32px·본문 13px)와 다르다.
  3. **가운데 "채팅방목록" 열이 거의 비어 있음**: "전체"(말풍선 아이콘)와 "테스트관리자" 두 줄뿐이고, "전체"가 채팅방인지 필터인지 구분되지 않는다. 왼쪽의 필터 "전체 2"와도 이름이 겹친다. 마지막 메시지 미리보기·시간·안읽음 배지가 없다.
  4. **왼쪽 열과 가운데 열이 같은 폭(약 335px)**이라 위계가 없고, 오른쪽 대화 영역은 거대한 빈 회색 공간에 작은 회색 안내문 한 줄뿐이다. 승인된 빈 화면 규칙(StateView: 제목 + 설명 + 행동 버튼)이 적용되지 않았다.
  5. 상단 제목이 `그룹웨어 > 메신저`로 페이지 제목 규칙(15px)과 다르게 보이고 잘려 있다(캡처 위쪽이 잘렸을 수 있음 — 확인 못 함).
- **확인 못 함**: 이 캡처는 대화창이 열리지 않은 첫 화면이다. 대화창(말풍선·입력 줄·첨부) 모양은 보지 못했다 — 작업 시작 때 대화창 화면도 캡처해서 함께 점검한다.
- **코드 사실**: 메신저는 `src/components/erp/messenger-page.tsx`와 `src/components/erp/messenger/modern.tsx`(모던 전용)로 되어 있다.
- **결정 대기(추천안 — B형 규칙 준수)**:
  - **B형(3분할)을 그대로 지킨다**: 왼쪽 = 필터 열(전체·안읽음·1:1·그룹·알림 꺼짐, 건수), 가운데 = 목록, 오른쪽 = 대화창.
  - **가운데 열 위에 `[채팅방 | 사원]` 전환 버튼 하나**를 둔다. 사원 목록은 왼쪽 열 아래가 아니라 이 전환의 "사원" 쪽으로 옮긴다(검색은 가운데 열 맨 위 하나).
  - **채팅방 행**: 아바타 + 이름 + 마지막 메시지 한 줄 + 시간 + 안읽음 배지. **사원 행**: 아바타 + 이름 + 부서, 누르면 1:1 대화 시작.
  - **빈 화면**: 대화창이 비었을 때 StateView 형태(제목 "대화를 선택하세요" + 설명 + [새 대화] 버튼).
  - **행 높이·글자**: 규칙표 값(항목 32px·본문 13px·아바타 28px), 열 폭은 왼쪽 필터 열을 좁게(약 180px) 줄여 위계를 만든다.
  - 장점: 새 예외 변형이 필요 없고 B형을 쓰는 다른 화면(할일·메일·게시판)과 같은 틀이 된다. 단점: 사원 목록이 한 번 눌러서 전환해야 보인다(지금은 항상 보임).
  - 대안(원하면): 카카오톡식 2열(왼쪽에 [대화|사원] 탭 + 오른쪽 대화창). 더 단순하지만 B형 필터 열이 없어져 새 예외 변형 `messenger-split` 승인이 필요하다.
- **같은 구조(전수 전 확인)**: B형 화면 5개(할일·메일·게시판·공지·메신저) 중 메신저만 사원 목록 열이 따로 있다. 대화창 부품이 알림·모달(메신저 알림 등)과 공유되는지는 확인 못 함 — 작업 시작 때 센다.

## R-007 · "새 ○○" 버튼 위치가 화면마다 제각각 — 문서 양식 관리 포함 — 상태: 대기(기록만, 코딩 전)

- **발견(사용자, 2026-11-23, 문서 양식 관리 캡처)**: 문서 양식 관리는 `F2 새 양식`이 **페이지 제목줄 오른쪽 위**(`ESC 문서함으로`와 나란히)에 있다. 게시판은 `+ 새 공지` 등이 **목록 열 안**에, 매출 목록은 **도구 줄**에 있다. "기존 게시판이랑 달라서 애매하다."
- **판단: 규칙 위반이자 규칙의 빈틈이다.** 승인된 규칙은 "신규는 도구 줄의 [신규] 하나 → C형 모달"인데, B형(소통형) 화면에서는 그 자리가 정해져 있지 않아서 화면마다 다르게 만들어졌다. **같은 동작(새로 만들기)의 위치가 최소 3곳으로 갈라져 있다**: ① 도구 줄(매출·거래처 등) ② 목록 열 안(게시판) ③ 제목줄 오른쪽(문서 양식 관리).
- **캡처에서 보이는 다른 어긋남(문서 양식 관리)**
  1. 오른쪽 칸이 항상 **"양식 등록" 입력 폼**(R-005의 게시판 인라인 수정과 같은 문제). 읽기 전용 상세 + 모달이어야 한다.
  2. 목록 위 검색: 라벨 `양식 이름 검색`과 입력칸 안 문구 `양식 이름으로 검색`이 **같은 말을 두 번** 쓴다.
  3. 위쪽 파란 안내 박스가 길고 작은 글자(법무 문구) — 중요한 경고를 작은 글자 한 줄로 묻고 있다.
  4. 제목줄 버튼 `ESC 문서함으로`는 다른 화면에 없는 **이동 버튼 + 단축키 라벨** 조합이다(탭·메뉴로 이동하는 규칙과 다름).
  5. 단축키 라벨: 저장 `F7 등록`, 새로 `F2 새 양식` — F2는 "표 안 F2 = 셀 편집" 결정(R-003)과 충돌.
- **코드로 센 것(전수 1차)**: `ToolbarKey`/F2 "새 ○○" 계열을 쓰는 파일이 약 16곳(문서 양식 목록 `document-template-list-body.tsx`, 게시판 `board/page.tsx`, 할일 `todos/modern.tsx`, 인사문서 `hr/documents/*`, 결재선 `approvals/lines/*`, 부서 `settings/departments`, 공문 `official-documents/*`, 영업활동 `sales-activities/*`, 달력 등). 도구 줄 공용 부품(`ListActionToolbar`/`PageToolbar`)을 쓰는 것은 6개 파일뿐이다. 작업 시작 때 화면별로 다시 센다.
- **결정 대기(추천안)**: **모든 "새 ○○"는 도구 줄의 `[신규]` 하나로 통일**한다(규칙에 명문화).
  - 유형이 여러 개인 화면(게시판: 공지·인사문서·공문·기안)은 `[신규 ▾]` 메뉴로, 하나뿐인 화면(문서 양식 관리: 양식)은 `[신규]`.
  - 누르면 C형 "새 ○○" 모달(시안 H1/H2). 오른쪽 칸은 읽기 전용 상세.
  - 제목줄 오른쪽에는 버튼을 두지 않는다(제목 + 필요하면 상태 표시만).
  - 단점: 지금 제목줄이나 목록 열에서 바로 누르던 습관이 바뀐다. 장점: 어느 화면에서든 같은 자리·같은 이름이라 학습이 한 번으로 끝나고, 이 규칙을 자동 검사(제목줄·목록 열 안 "새 ○○" 금지)로 막을 수 있다.
- **연관**: R-003(도구 줄·단축키), R-005(게시판). 세 건은 **같은 규칙으로 한 번에** 처리하는 것이 맞다 — 개별로 고치면 또 어긋난다.

## R-008 · 도구 줄 자리가 화면마다 생겼다 사라져 메뉴 이동 때 화면이 밀림 — 상태: 대기(기록만, 코딩 전)

- **발견(사용자, 2026-11-23)**: "출고관리 눌렀을 때만 회사명 아래에 신규… 버튼이 늘어난다. 완전 개판이다."
- **원인(코드 확인)**: 앱 틀의 도구 줄 자리(`.erp-toolbar-slot`)는 그 화면이 `ListToolbar`/`PageToolbar`/`ListActionToolbar`를 그릴 때만 채워지고, 비어 있으면 `.erp-toolbar-slot:empty { display: none }`으로 **자리 자체가 사라진다**(`src/app/erp-theme.css`). 도구 줄을 그리는 화면은 매출·매입·거래처·공급처·미수금·할일·인사문서·공문·공지 등 약 13개 파일뿐이고 재고·대시보드·설정 등은 그리지 않는다 → 메뉴를 옮길 때마다 **화면 전체가 위아래로 밀린다**(약 42px). 매출은 버튼이 5개라 더 눈에 띈다(R-003).
- **판단: 규칙의 빈틈.** 승인된 시안(type-A)은 도구 줄이 모든 화면에서 항상 같은 자리·같은 높이에 있는 구조다. "있을 수도 없을 수도 있는" 자리는 시안에 없다.
- **결정 대기(추천안)**: 도구 줄을 **항상 보이게(높이 42px 고정)**. 버튼이 없는 화면은 오른쪽에 상태 문구만(건수·조회 시각 등). 장점: 메뉴 이동 때 화면이 밀리지 않고 신규·조회 위치가 모든 화면에서 같다. 단점: 버튼 없는 화면에서 도구 줄이 비어 보인다.
- **임시 완화(승인 대기)**: CSS에서 `.erp-toolbar-slot:empty`를 숨기지 않고 최소 높이만 유지 → 밀림 즉시 해소. 버튼 정리는 R-003·R-005·R-007과 한 묶음.
- **같은 구조(전수)**: 도구 줄 자리를 쓰는 화면 약 13개 파일 vs 안 쓰는 화면 약 110개(전체 화면 129개 기준). 규칙표 점검에 "화면 이동 시 본문 시작 위치(y)가 같은가"를 추가한다.
- **연관**: R-003, R-005, R-007.

## R-009 · 모서리 둥글기(R값)가 매출관리와 그룹웨어에서 다름 — 상태: 대기(기록만, 코딩 전)

- **발견(사용자, 2026-11-23)**: 매출관리의 R값과 그룹웨어의 R값이 통일되어 있지 않다.
- **원인(코드 확인): 둥글기 토큰이 두 갈래다.**
  1. **일반 토큰** `--erp-radius-xs…4xl` — 매출·거래처·재고 등. 규칙표 4단계(3/5/6/8/12px)로 정리했다. 쓰는 CSS 규칙 112개.
  2. **소통형(그룹웨어) 전용 토큰** `--erp-comm-radius`, `-row`, `-pill`, `-bubble`, `-sm` — 게시판·메일·메신저·할일 등. 쓰는 CSS 규칙 35개. 값은 **규칙표 작업에서 손대지 않았다**: 모던에서 `--erp-comm-radius: 0`(각진 카드), `-row: 0`(각진 행), `-pill: 5px`, `-bubble: 14px`, `-sm: 5px`.
  - 결과: 같은 "카드·행·칩"이 매출 쪽은 8px·6px로 둥글고, 그룹웨어 쪽은 0px로 각지거나 14px로 크게 둥글어 **한 앱 안에서 모서리 모양이 두 종류**가 된다.
- **판단: 규칙 위반.** 규칙표는 모서리를 4단계(작은 3~5 / 중간 6 / 카드 8 / 모달 12) + 알약만 허용한다. 소통형 전용 토큰은 그 밖의 값이다.
- **결정 대기(추천안)**
  - 소통형 전용 토큰을 **없애고 일반 토큰으로 합친다**: 카드 → 카드(8), 행 → 중간(6), 알약 → 알약, 말풍선 → 모달 단계(12), 작은 것 → 작은(5).
  - 자동 검사 추가: `--erp-comm-radius*` 새 사용 금지, 모서리는 일반 토큰 단계만.
  - 단점: 그룹웨어 화면이 지금보다 둥글어진다(각진 느낌이 사라짐). 메신저 말풍선은 12px로 약간 작아진다(14 → 12).
- **같은 구조(전수)**: `--erp-comm-radius*` 사용 규칙 35개(소통형 화면 5개: 할일·메일·게시판·공지·메신저). 규칙표 점검에 그룹웨어 화면(게시판·메신저·메일·공지·문서 양식)의 카드·행 모서리 측정을 추가한다.
- **연관**: R-004(메뉴·대시보드 글자), R-005~007(그룹웨어 화면 규칙). 그룹웨어 화면은 모서리·버튼 위치·수정 방식 3가지가 한 번에 어긋나 있으므로 **그룹웨어 묶음**으로 함께 처리하는 것이 맞다.

## R-010 · "열 설정"(구매 견적요청 등)과 "컬럼 설정"(매출·매입)이 같은 기능인데 이름·부품·저장 방식이 다름 — 상태: 대기(기록만, 코딩 전)

- **발견(사용자, 2026-11-23)**: 구매 견적요청의 "열 설정"과 매출의 "컬럼 설정"이 같은 기능 아니냐.

- **코드 확인**

- **결정 대기(추천안)**: **하나로 합친다.**
  - 이름은 **"열 설정"**(앱 전체가 "열"을 쓰므로). 메뉴 안은 체크박스 목록 + `(N개 숨김)` 표시로 통일.
